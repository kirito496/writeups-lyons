# PWN#005 — "Document Store" (<HOST>:<PORT>) — 150 pts

**Auteur :** lyons

> Objectif : *Get a shell on the remote host and read the flag.*
> Mode : distant autorisé par l'utilisateur. Aucun binaire fourni (blind pwn).
> Statut : **recon complète, exploitation bloquée** (voir § Blocage). Flag non obtenu.

## Observation du service

Le menu tourne en boucle au fil d'une connexion :

```
=== Document Store ===
1) Peek memory  2) Checkout
>
```

### Option 1 — Peek memory (lecture mémoire arbitraire, plafonnée)

- Invites : `Address: ` puis `Length: `.
- Entiers analysés par `strtol(.., 0)` : formats `0x..`, octal `0..` et décimal acceptés ; `abc`/`0b..` donnent 0.
- Contrôle de `Length` : plage **1..1024** imposée (0 ou au-delà d'un maximum → `Invalid length.` ; 4096 rejeté, 1024 accepté).
- Comportement : l'équivalent de `write(1, addr, len)`. Une adresse non mappée rend **0 octet** sans crash (copie sûre façon `write()` qui EFAULT). La **lecture arbitraire est donc réelle, mais une adresse valide reste indispensable**.
- Aucune adresse fixe lisible débusquée (sérialisé) : ni `0x400000+` d'un non-PIE, ni les valeurs ASLR-off habituelles `0x5555...`, `0x7ffff7...`. ⇒ **PIE + ASLR actifs**.

### Option 2 — Checkout (débordement de pile)

- Invites : `Leave a note before you go: `, puis `Thanks for visiting.`
- Lecture assurée par `read(0, buf, N)` (comptage/EOF, **pas** ligne) : transmettre les octets exacts puis `shutdown(write)` procure un contrôle propre, sans pollution par `\n`.
- La note **n'est jamais ré-affichée** (aucune fuite par écho).
- Agencement : `buf[72] | canary[8]@72 | saved_rbp@80 | ret@88`.
  - `'A'*72` passe ; `'A'*73` fait crasher (l'octet 72 est le **canary**, LSB `0x00` : seul `byte0=0x00` survit 8/8).
  - Sans la valeur du canary, pas de ROP possible.

### Options dissimulées 7 et 9 — `session: <V1> <V2>`

- Deux valeurs 64 bits par option : **figées le temps d'une connexion**, **re-randomisées à chaque nouvelle session**.
- Invariants relevés (sur 24 connexions et plus) :
  - `7V1 ^ 9V1 == 0x0b`, **constant** (un même objet masqué, distant de 11 octets).
  - `7V1,7V2,9V1` arborent les mêmes 48 bits de poids fort le temps d'une connexion (KEY XOR commun).
  - `7V1 ^ 7V2` = `0x14fe`, agrémenté de bits variables aux positions 13..20.
  - `7V2 ^ 9V2` : des régions distinctes.
- Lecture finale : chaque valeur vaut `réel ^ KEY_par_connexion` (XOR, pas de rotation, la proximité étant préservée). Sans **une** valeur réelle d'ancrage, KEY ne s'inverse pas.

## Négatifs confirmés

- Le menu, Address, Length et la note sont tous sains : aucun point de format string.
- Les entrées Address / Length / menu, toutes bornées, n'offrent aucun débordement.
- Canary **re-randomisé à chaque connexion** (exécution par connexion) : brute / BROP / stack-reading **tombent à l'eau** (elles exigeraient une stabilité d'une connexion à l'autre).
- Une seule tentative de canary par connexion (canary erroné → `__stack_chk_fail` → abort → socket coupée).

## Blocage

La chaîne logique impose de tout réaliser en **une** connexion — canary et ASLR changent dès la suivante :
1. une fuite fournissant une adresse valide afin d'amorcer Peek ;
2. Peek → lecture de la pile → **canary** + une adresse (PIE ou libc) ;
3. overflow de Checkout : `72*pad + canary + rbp + ROP ret2libc` → shell.

Le maillon manquant demeure **l'amorce de Peek**. L'unique fuite disponible (`session`, options 7/9) se cache derrière un KEY propre à chaque connexion ; aucune valeur réelle d'ancrage n'a surgi des tentatives à l'aveugle, et aucune adresse fixe ne se laisse lire (ASLR actif).

## De quoi débloquer la situation

- **Le binaire du challenge** (et sa libc) : ils livreraient (a) la borne et la sémantique exactes de Peek, (b) ce que `session` encode réellement ainsi que le KEY, (c) les offsets et gadgets. L'exploitation deviendrait alors directe (ret2libc nourri d'une Peek-leak + overflow).
- À défaut : confirmer s'il existe un autre point d'entrée (fichier téléchargeable sur la plateforme CTF).

## Reproduction (scripts conservés dans le scratchpad de session)

- Cartographie offset/canary : payload `b'A'*72 + <canary8>` expédié via `send()+shutdown('send')`.
- Peek : `1\n` puis `Address:` `0x..\n` puis `Length:` `1..1024\n`.
- Fuite session : `7\n` ou `9\n`, d'où la ligne `session: 0x.. 0x..`.
